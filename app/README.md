# 상호작용형 이력서 자동 생성 — 실시 앱

특허 출원 「이력 결측치 탐색 및 데이터 통합 기반의 상호작용형 이력서 자동 생성
시스템 및 그 방법」의 구성요소를 **사용자 단말에서 동작하는 형태**로 구현한 것이다.
연구용 스크립트(`../src`)가 배치 처리였던 것과 달리, 여기서는 질의–응답–병합–
미리보기–확정이 화면에서 순차로 일어난다.

```
app/
  backend/
    main.py       FastAPI — 세션 API, 정적 파일 서빙
    engine.py     세션 상태 기계 (탐지 → 질의 → 파싱 → 병합 → 미리보기 → 확정)
    normalize.py  데이터 형식 변환부(114) — LLM 정규화 + 규칙 폴백
  frontend/
    src/App.jsx  화면 2개 (질의·응답 / 미리보기·확정)
    src/api.js   API 클라이언트
```

## 정규화기 (114)

원문을 레코드로 옮기는 경로가 두 가지다.

| 모드 | 동작 |
|---|---|
| `rules` | 정규식 파서만. 외부 호출 없음 |
| `llm` | 언어 모델에게 **정규화만** 시키고 부재 판단은 규칙이 수행. 실패 시 오류 |
| `auto` | 키가 있으면 llm, 실패하면 rules 로 되돌아감 (기본값) |

규칙 파서는 표기가 흔들리면 무너진다. 실제 이력서에서 `~.` 오타 하나로 경력 두 건이
누락되고, 그 여파로 공백 구간이 잘못 계산되는 것을 확인했다. LLM 정규화는 이런
표기 흔들림을 흡수한다. 논문 실험에서도 같은 구성이 직접 탐지(F1 0.31~0.38)보다
크게 앞섰다(F1 0.87~0.93).

어느 경로를 탔는지는 세션 생성 응답의 `normalizer.path` 와 `source` 에 남는다.

### 설정

```bash
cp .env.example .env    # 저장소 루트
# ANTHROPIC_API_KEY 를 채우면 auto 모드에서 LLM 정규화가 켜진다
```

`.env` 는 `.gitignore` 에 있어 저장소에 올라가지 않는다. 키가 없으면 경고 없이
규칙 파서로 동작하므로, 키 없이도 앱 전체를 시험할 수 있다.

## 실행

```bash
# 1) 말뭉치가 없으면 먼저 생성
python3 src/generate.py --n 600 --seed 42 --out output/resumes.jsonl

# 2) 백엔드
pip install fastapi uvicorn
uvicorn app.backend.main:app --port 8000

# 3) 프런트엔드 — 개발 모드 (HMR, /api 는 8000 으로 프록시)
cd app/frontend
npm ci            # vite 는 devDependency 라 설치를 건너뛰면 "vite: not found"
npm run dev                                       # http://localhost:5173

# 3') 또는 빌드해서 백엔드가 함께 서빙
cd app/frontend && npm ci && npm run build        # http://localhost:8000
```

### 소스를 고쳤는데 화면이 그대로일 때

`dist/` 는 저장소에 포함되지 않는다(`.gitignore`). **`git pull` 로는 화면이 갱신되지
않으며, 반드시 다시 빌드해야 한다.**

```bash
cd app/frontend && npm run build     # 서버 재시작 불필요, 새로고침만
curl -s localhost:8000/api/health | python3 -m json.tool   # frontend.built_at 확인
```

`/api/health` 의 `frontend.built_at` 과 `assets` 가 지금 서빙 중인 빌드를 알려준다.
빌드 시각이 과거면 빌드가 안 된 것이다.

`index.html` 은 `no-store` 로, 해시가 붙은 자산은 `immutable` 로 서빙하므로 브라우저
캐시 때문에 옛 화면이 남는 일은 없다. 개발 모드(`npm run dev`)에서는 빌드가 필요 없다.

### 두 방식의 차이

| | 개발 모드 (`npm run dev`) | 빌드 서빙 (`npm run build`) |
|---|---|---|
| 접속 주소 | `localhost:5173` | `localhost:8000` |
| 띄우는 서버 | Vite + uvicorn 둘 다 | uvicorn 하나 |
| `/api` 요청 | Vite 가 8000 으로 프록시 | 같은 서버라 프록시 불필요 |
| 코드 수정 | 즉시 반영(HMR) | 다시 빌드해야 반영 |
| 용도 | 개발 | 시연·증빙 캡처 |

## 백엔드가 dist 를 서빙하는 방식

`npm run build` 는 `app/frontend/dist/` 에 `index.html` 과 해시가 붙은 자산
(`assets/index-XXXX.js`, `assets/index-XXXX.css`)을 만든다. 백엔드는 이 폴더를
두 개의 라우트로 내보낸다(`app/backend/main.py` 하단).

```
GET /assets/{path}   dist/assets/ 아래 파일을 그대로 반환
GET /{path}          /api 로 시작하지 않는 모든 경로 → dist/index.html
```

두 번째 라우트가 **SPA 폴백**이다. React 앱은 주소가 `/` 든 `/preview` 든 같은
`index.html` 을 받아 화면을 그리므로, 어떤 경로로 들어와도 앱이 뜨고 새로고침해도
404 가 나지 않는다. API 라우트가 파일보다 먼저 선언되어 있어 `/api/...` 는 이 폴백에
걸리지 않는다.

`dist` 존재 여부는 **서버 시작 시점이 아니라 요청 시점에** 확인한다. 서버를 먼저
띄우고 나중에 빌드해도 새로고침만 하면 되고, 재시작할 필요가 없다. 아직 빌드하지
않았다면 `/` 가 503 과 함께 빌드 방법을 안내하는 페이지를 반환한다 — 흰 화면이나
404 대신 원인이 바로 보인다.

경로 검증도 걸려 있다. `/assets/../../etc/passwd` 같은 요청은 정규화 후 `dist/assets`
바깥을 가리키므로 404 로 막힌다.

## 화면

**⓪ 시작** — 무작위 샘플을 **한 건씩** 보여준다. 이름·직군·결측 건수와 유형이 요약으로
보이고, 이력서 본문은 접혀 있어 필요할 때만 펼친다. 오른쪽 "다른 이력서 뽑기" 로 다음
후보로 넘어가며, 후보 5건을 미리 받아 두었다가 소진되면 새로 가져온다. 본문을 직접
붙여넣는 입력도 접어 두어, 시작 화면이 한눈에 들어오게 했다.

**① 질의 · 응답** — 결측 하나를 골라 자연어 질문으로 보여준다. 질문 순서는 이득
정렬(`가중치 × 덮는 필드 수`)을 따른다. 답변을 제출하면 파싱된 필드가 바로 아래에
표시되므로, 시스템이 무엇을 어떻게 이해했는지 사용자가 확인할 수 있다. 답변마다
재탐지가 일어나므로, 날짜 질문에 답하면 그 안에 가려져 있던 경력 공백이 새 질문으로
큐에 들어온다.

답변 입력창 아래의 **"예시 문장 만들기"** 를 누르면 초안 3개가 나온다. 다시 누르면
이전과 다른 문장이 나오고, 초안을 누르면 입력창에 이어 붙는다(덮어쓰지 않는다).

초안은 **사실을 담지 않는다.** 빈칸(`____`)이 있는 문장 틀만 제공하며, 직무명·수치·
성과처럼 사용자만 아는 값은 언제나 비워 둔다.

```
✗  "파이프라인을 재설계해 처리 시간을 35% 줄였습니다"   ← 수치를 지어냄
✓  "제가 ____을(를) 맡았고, ____을(를) ____% 개선했습니다"
```

이력서는 고용주에게 제출하는 문서다. 그럴듯한 경력 사실을 자동으로 만들어 주면
사용자가 그대로 제출할 위험이 있고, 그 순간 보완 도구가 아니라 허위 기재 도구가 된다.
API 키가 있으면 LLM 이 문장 틀을 만들고(배지 `LLM 생성`), 없으면 내장 틀을
사용한다(`문장 틀`). 어느 쪽이든 빈칸 규칙은 동일하며, LLM 경로에도 사실을 지어내지
말라는 지시가 시스템 프롬프트에 들어 있다.

**② 미리보기 · 확정** — 병합된 레코드를 이력서 서식으로 배치해 보여준다. 아직 비어
있는 항목은 붉게 표시되어 **확정 전에 무엇이 비었는지 사용자가 판단**할 수 있다.
확정 버튼을 누르면 확정 시각이 기록되고 편집이 잠긴다.

## 정규화 경로 표시

데이터 형식 변환부(114)가 어느 경로를 탔는지 화면 상단 배지에 표시한다.

| 배지 | 의미 |
|---|---|
| **LLM 정규화** (초록) | 하이브리드 경로. 모델이 원문을 레코드로 옮겼다 |
| **규칙 파서** (주황) | 정규식 파서만 사용. 키가 없거나 LLM 호출이 실패한 경우 |
| **말뭉치 레코드** (회색) | 샘플 모드. 이미 구조화되어 있어 변환 단계가 없다 |
| **정규화 실패** (빨강) | `NORMALIZER=llm` 에서 호출이 실패 |

배지에 마우스를 올리면 설정 모드, 모델명, API 키 설정 여부, 폴백 사유, 소요 시간이
보인다. `auto` 모드는 키가 잘못되어도 조용히 규칙 파서로 되돌아가므로, 이 배지가
없으면 LLM 이 도는 줄 알고 규칙 파서 결과를 보게 된다. 논문 실험에서 두 경로의
F1 차이가 0.31 대 0.93이었던 만큼 구분이 필요하다.

## API

| 메서드 | 경로 | 대응 구성요소 |
|---|---|---|
| GET | `/api/samples?n=3` | 무작위 샘플 후보 + 본문 (시작 화면) |
| POST | `/api/sessions` | 수집부(110), 데이터 형식 변환부(114) |
| GET | `/api/sessions/{id}/info` | 정규화 경로, 설정, 현재 이력서 본문 |
| GET | `/api/sessions/{id}/next` | 결측치 탐색부(121), 질의 프롬프트 생성부(122) |
| POST | `/api/sessions/{id}/suggest` | 답변 초안 (빈칸 문장 틀) |
| POST | `/api/sessions/{id}/answer` | 답변 파싱부(131) → 데이터 병합부(134) |
| GET | `/api/sessions/{id}/preview` | 문장 생성부(135), 템플릿 배치부(136) |
| POST | `/api/sessions/{id}/confirm` | 확정 신호 수신(137) |
| GET | `/api/sessions/{id}/trace` | 질의–답변–파싱 이력 (증빙용) |

세션 생성은 세 가지 모드를 받는다. `sample` 은 말뭉치에서 하나를 고르고,
`document` 는 이력서 본문 텍스트를 파싱하며, `record` 는 이미 정규화된 레코드를
그대로 받는다.

| 2 | 데이터 형식 변환부(114) | ✅ | `normalize()` — LLM/규칙 2경로 |
| 3·4 | 기간적 공백기 탐색부(1211) | ✅ | `detect_eval.detect()` |

해소된다.

## 증빙 자료 만들기

`/api/sessions/{id}/trace` 가 질의–답변–파싱–병합 전 과정을 시각과 함께 반환한다.
세션 하나를 끝까지 진행한 뒤 이 응답을 저장하면, 청구항 5의 각 단계가 실제로
수행되었음을 시각 순서대로 보일 수 있다.

## 한계

- 세션은 메모리에만 있다. 서버를 재시작하면 사라진다. 운영에는 저장소가 필요하다.
- 수집 단계의 정규화는 하이브리드로 교체했으나, **답변 파싱(131)은 아직 규칙 기반**이다.
  같은 이유로 이쪽도 LLM 경로를 두는 편이 낫다.
- 문장 생성부(135)는 현재 필드를 잇는 수준이다. 근거 제약을 유지한 채 문장 품질을
  올리는 것이 다음 과제다.
